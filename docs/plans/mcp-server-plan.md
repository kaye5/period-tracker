## Global constraints (apply to every task)

1. **Calendar days are `YYYY-MM-DD` civil dates** (`CivilDate` from `lib/date/civil.ts`) and are
   never converted to instants. Only `lib/date/civil.ts` may construct `Date` objects inside
   `lib/engine`, `lib/stat`, `lib/date` (enforced by `engine-purity.test.ts`).
2. **No code may use the host's time zone.** `Intl.DateTimeFormat().resolvedOptions().timeZone`
   is allowed only in browser code under `components/` (e.g. `clientToday`).
3. **Instants are UTC** (`Date.now()` epoch ms; DB `DATETIME(3)` in UTC; wire ISO 8601 `…Z`).
4. Keep every existing behaviour and data path: same `dayLogSchema` validation, same
   `upsertDayLog`, same engine (`computeEverything`). No engine constants change.
5. Pure logic lives in `lib/` with a colocated `*.test.ts`; I/O only at route/handler edges.
6. Never edit files outside the task's list without saying why in the report. Stage files
   explicitly by path — never `git add -A` / `git add .`.
7. Copy comes from `lib/copy`; no new health claims, no health advice.
8. Each task ends with `pnpm typecheck`, `pnpm lint`, and `pnpm test` passing (all suites, not
   just new ones), then one commit whose message ends with:
   `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`

### Task 1: Time primitives — instant formatting and time-zone resolution

Spec: "Part A — Time zone".

Files:
- `lib/date/civil.ts` (add one function)
- `lib/date/civil.test.ts` (add tests)
- `lib/time/userTimeZone.ts` (new)
- `lib/time/userTimeZone.test.ts` (new)

1. In `lib/date/civil.ts` add
   `export function formatInstant(epochMs: number, tz: string): { utc: string; local: string }`.
   - `utc`: ISO 8601 with milliseconds and `Z`, e.g. `"2026-11-13T23:30:00.000Z"`.
   - `local`: the same instant as wall-clock time in `tz` with its numeric offset,
     `YYYY-MM-DDTHH:mm:ss.SSS±HH:MM` (UTC renders `+00:00`, never `Z`). Use `Intl.DateTimeFormat`
     (e.g. `timeZoneName: "longOffset"` → `"GMT+07:00"`, where plain `"GMT"` means `+00:00`).
   - Required test cases (exact strings):
     - `Date.UTC(2026,10,13,23,30)` in `Asia/Bangkok` → local `"2026-11-14T06:30:00.000+07:00"`
     - same instant in `America/New_York` → `"2026-11-13T18:30:00.000-05:00"`
     - same instant in `Asia/Kathmandu` → `"2026-11-14T05:15:00.000+05:45"`
     - same instant in `UTC` → `"2026-11-13T23:30:00.000+00:00"`, utc `"2026-11-13T23:30:00.000Z"`
     - DST: `Date.UTC(2026,2,8,7,30)` in `America/New_York` → `"2026-03-08T03:30:00.000-04:00"`
     - `todayInZone` agrees with the date part of `local` for all of the above.
2. Create `lib/time/userTimeZone.ts`:
   ```ts
   export type TimeZoneSource = "input" | "cookie" | "profile" | "fallback_utc";
   export function isValidTimeZone(tz: unknown): tz is string;
   export function resolveTimeZone(c: { input?: unknown; cookie?: unknown; profile?: unknown }):
     { timeZone: string; source: TimeZoneSource };
   ```
   - Valid = a non-empty string ≤ 64 chars that `new Intl.DateTimeFormat("en-US", { timeZone })`
     accepts (catch the `RangeError`). Never throws.
   - Order: `input` → `cookie` → `profile` → `{ timeZone: "UTC", source: "fallback_utc" }`;
     invalid candidates are skipped.
   - Tests: order, each invalid kind skipped (`""`, `"Not/AZone"`, `123`, `null`, 65-char string),
     fallback flagged, `"UTC"` and `"Asia/Bangkok"` valid.

Verify: `pnpm exec vitest run lib/date lib/time` then the global checks.
